# `corvid_vector`

Deterministic fixed-point 3-vectors for
[Corvid](https://github.com/peasanttide/corvid), built on
[`corvid_fixed`](https://docs.rs/corvid_fixed). Four concrete types and one
packed one, no generics, every operation `const` and integer-only — so the same
inputs give the same bits on every machine running the simulation.

```rust
use corvid_fixed::{I24F8, I48F16};
use corvid_vector::{GlobalFinePoint, GlobalPoint};

// A camera on the earth's surface, and a point a millimetre from it.
let camera = GlobalFinePoint::splat(I48F16::from_f64(6_371_000.0));
let target = camera + GlobalFinePoint::new(
    I48F16::from_f64(0.001),
    I48F16::ZERO,
    I48F16::ZERO,
);

// The offset is exact: the range is spent on the absolute position, and the
// near-field difference still resolves to the last bit.
let offset = target - camera;
assert_eq!(offset.x().to_bits(), I48F16::from_f64(0.001).to_bits());

// Squared lengths come back in the widened intermediate, not the component
// type — see below for why that is not a mistake.
let p = GlobalPoint::new(I24F8::from_f64(3.0), I24F8::from_f64(4.0), I24F8::ZERO);
assert_eq!(p.length(), I24F8::from_f64(5.0));

// Normalizing is the one operation that can fail, and only at zero.
assert_eq!(GlobalPoint::ZERO.normalize(), None);
let unit = p.normalize().expect("non-zero");
assert!((unit.x().to_f64() - 0.6).abs() < 1e-6);

// A unit direction also packs into two bytes, for a mesh vertex.
let packed = corvid_vector::OctDirection::encode(unit);
assert_eq!(core::mem::size_of_val(&packed), 2);
```

## The types

| Type | Component | Range | Resolution | Role |
|---|---|---|---|---|
| [`GlobalFinePoint`] | `I48F16` | ±1.407e14 m | 15.26 µm | Camera and VR pose position |
| [`GlobalPoint`] | `I24F8` | ±8388 km | 3.9 mm | Object position; everyday offset |
| [`FinePoint`] | `I16F16` | ±32.7 km | 15.26 µm | Render and VR near-field |
| [`Direction`] | `Signed32` | unit | 4.7e-10 | Unit directions and rotation axes |
| [`OctDirection`] | two `Signed8` | unit | 0.9569° | A unit direction in a mesh vertex |

The names read as two independent axes: *Global* means wide range, *Fine* means
high resolution. [`GlobalFinePoint`] is both, and pays for it in width;
[`GlobalFinePoint`] and [`FinePoint`] share a resolution and differ only in
range.

Points double as offsets. There is no separate point/vector distinction — the
same choice Godot and Unity make, and a separate `GlobalPointOffset` would
double the API for no caught bug.

The first four are a `#[repr(C)]` array of three scalars, generated by one
macro. Concrete rather than generic, because `const fn` cannot take trait
bounds and every operation here is `const`. [`OctDirection`] is not one of them:
it is a codec rather than a vector, and it is described below.

## Building one

Each type has a lowercase free function named for it, taking anything that
converts into its component — which for the three position types includes bare
integers, since [`corvid_fixed`](https://docs.rs/corvid_fixed) gives each scalar
a `From` from the widest integer type it holds exactly.

```rust
use corvid_fixed::I16F16;
use corvid_vector::{FinePoint, GlobalPoint, finepoint, globalpoint};

// The three ways, all the same value.
let a = finepoint(1, 2, -3);
let b = FinePoint::from((1, 2, -3));
let c = FinePoint::from([1, 2, -3]);
assert_eq!(a, b);
assert_eq!(b, c);

// One component per type parameter, so a computed axis does not force the
// other two to be spelled out.
let mixed = finepoint(I16F16::from_f64(0.5), 0, -1);
assert_eq!(mixed.x(), I16F16::from_f64(0.5));

// And the integer really is the value rather than the bit pattern.
assert_eq!(globalpoint(1, 0, 0).x(), corvid_fixed::I24F8::from_f64(1.0));
assert_eq!(GlobalPoint::from((1, 0, 0)).x().to_bits(), 256);
```

Which integer each type takes follows from its scalar: [`FinePoint`] and
[`GlobalPoint`] take `i16`, [`GlobalFinePoint`] takes `i32`, and [`Direction`]
takes no integer at all, because no integer type has a range inside `-1.0 ..=
1.0`. `corvid_fixed`'s README says why the set is one type per scalar rather
than every type that would convert exactly; the short version is that a second
one stops `finepoint(1, 2, 3)` from compiling.

## Iterating

Components come out in **`x`, `y`, `z` order**, and the order is part of the
type. It is the same order in five places — the constructors, `to_array`,
`iter`, the digest, and the bytes on the wire — and `tests/construct.rs` pins
them to each other, because any one of them could be permuted alone and the
result would be geometry that is wrong rather than absent.

```rust
use corvid_fixed::I24F8;
use corvid_vector::globalpoint;

let mut p = globalpoint(1, 2, -3);
assert_eq!(p.iter().map(|c| c.to_f64()).sum::<f64>(), 0.0);

for component in &mut p {
    *component = component.abs();
}
assert_eq!(p, globalpoint(1, 2, 3));

// By value, by reference, and by mutable reference.
assert_eq!(p.into_iter().count(), 3);
assert_eq!(p.to_array()[2], I24F8::from_f64(3.0));
```

Nothing renormalizes after a write, so assigning through a [`Direction`]'s
`iter_mut` can leave it non-unit — exactly as [`Direction::new`] can, and the
same [`normalize`](Direction::normalize) fixes both.

## Squared length does not return the component type

The obvious signature is a trap. [`GlobalPoint`]'s components reach ±8388608,
so the raw sum of three squares reaches `3 × 2^62` — **past `i64::MAX`** — and
expressing the result back in `I24F8` would saturate for any vector longer than
**1672 m**. A `length_squared` that silently returns `MAX` for a 2 km offset is
worse than no `length_squared` at all.

So squared magnitudes return the widened *unsigned* intermediate, in units of
`DELTA²`:

```rust
use corvid_fixed::I24F8;
use corvid_vector::GlobalPoint;

let p = GlobalPoint::splat(I24F8::from_f64(2000.0));
let component = i64::from(I24F8::from_f64(2000.0).to_bits());
assert_eq!(p.length_squared(), 3 * (component * component) as u64);
```

`GlobalPoint::length_squared` and `FinePoint::length_squared` return `u64`;
`GlobalFinePoint::length_squared` returns `u128`. This is lossless over the
whole range and answers the question the operation is actually for — comparing
and sorting distances without a square root.

`length` and `distance` do return the component type, computed the way
`corvid_fixed::hypot` already does it: unsigned wide sum, one integer square
root, one rounding. Because a value is its bit pattern over a fixed scale, the
integer square root of the summed squares *is* the answer's bit pattern.

## Width conversions

```rust
use corvid_fixed::{I16F16, I24F8, I48F16};
use corvid_vector::{FinePoint, GlobalFinePoint, GlobalPoint};

// Exact: the target holds at least as much range and resolution.
let coarse = GlobalPoint::splat(I24F8::from_f64(1234.5));
assert_eq!(coarse.to_global_fine().to_global(), Some(coarse));

// Total but lossy: I16F16's whole range fits I24F8, at 3.9 mm instead of
// 15.26 um. Rounded once — half a coarse step rounds up.
let half_step = FinePoint::new(I16F16::from_bits(128), I16F16::ZERO, I16F16::ZERO);
assert_eq!(half_step.to_global().x().to_bits(), 1);

// Range-checked: None only when the value does not fit, never for magnitude
// quietly discarded.
let far = GlobalFinePoint::splat(I48F16::from_f64(40_000.0));
assert_eq!(far.to_fine(), None);
```

| Conversion | Behaviour |
|---|---|
| `GlobalPoint::to_global_fine` | exact, `bits << 8` |
| `FinePoint::to_global_fine` | exact, widen only |
| `FinePoint::to_global` | total, `bits >> 8`, rounded |
| `GlobalFinePoint::to_fine` | range only, **no rounding** |
| `GlobalFinePoint::to_global` | range-checked, rounded |
| `GlobalPoint::to_fine` | range-checked, exact |

[`GlobalFinePoint::to_fine`] is the important one. Because both types carry 16
fractional bits, it is a **pure range check on the integer part — `i64 as i32`
after a bounds test, with no rounding at all**. The near-field conversion a
renderer runs thousands of times per frame is exact by construction, not exact
within a tolerance.

## Normalizing

[`normalize`](GlobalPoint::normalize) returns `Option<Direction>`, and `None`
only for the zero vector — which has no direction, and is the sole failure.

Only the ratios of the components matter, so one implementation serves all four
widths without ever touching the component scale. Rescaling is a shift rather
than a divide, so the same direction at two magnitudes can differ in the last
bit or two — deterministic, not magnitude-independent to the bit. It costs one
[`I2F30::rsqrt`](corvid_fixed::I2F30::rsqrt), three multiplies and a few
shifts, with no division anywhere. The reduction it performs is why `I2F30`
has the shape it does: the sum of squares relative to the largest component
lands in `[0.25, 3]`, which does not fit a type that stops at `±2`, but an
even shift always brings it into `[0.25, 1)`, and `rsqrt` of *that* lands in
`(1, 2]`, which fits exactly.

## A unit direction in sixteen bits

[`Direction`] spends twelve bytes on a unit vector, which is right for a
rotation axis and wrong for a mesh vertex — a normal is one attribute of three
or four on every vertex of every mesh, and twelve bytes there is most of the
vertex. [`OctDirection`] is the storage form: **two bytes**, decoded on use.

```rust
use corvid_fixed::Signed32;
use corvid_vector::{Direction, OctDirection, direction};

let up = direction(Signed32::ZERO, Signed32::ZERO, Signed32::MAX);
let packed = OctDirection::encode(up);

// The six axes are corners of the octahedron, so they survive exactly.
assert_eq!(packed.decode(), up);
assert_eq!(packed, OctDirection::UP);

// Encoding is always spelled out. There is no `From<Direction>` and no
// `.into()` onto this type, because encoding rounds and a conversion that
// rounds says so at the call site — the same rule `corvid_fixed` states about
// integers and `from_f64`. Decoding has a `From`, because the sixteen bits name
// exactly one direction and nothing is being chosen between.
let back: Direction = packed.into();
assert_eq!(back, up);
```

The map is octahedral. Divide a direction by `|x| + |y| + |z|` to land on the
octahedron `|x| + |y| + |z| = 1`; the upper hemisphere's four faces then unfold
onto the diamond `|u| + |v| <= 1`, and the lower four fold *outward* into the
corners of the square `[-1, 1]²`. The square is what gets quantized, and it is
nearly area-preserving — which is the whole reason to prefer this to a
latitude/longitude pair at the same width, since that spends most of its
resolution near the poles, where the sphere has least area.

Encode and decode are integer-only: a sum, two multiplications by 127 and two
rounded divisions going in; a fold and the crate's own integer
[`normalize`](Direction::normalize) coming back. No floating point is involved
in either direction, so a mesh built on one machine has the normals a mesh built
on another does.

### What it costs

| | Degrees |
|---|---|
| Worst error, swept over the square | **0.9569** (measured 0.956822) |
| Mean error, swept over the square | 0.3284 |
| Worst error over the `z = 0` seam | 0.6431 (measured 0.643056) |
| Worst error over the outer edges of the square | 0.4512 (measured 0.451139) |
| Worst error, 2 × 10⁵ directions uniform on the sphere | 0.9467 (measured 0.946610) |
| Mean error, 2 × 10⁵ directions uniform on the sphere | 0.3370 (measured 0.337017) |

`cargo test -p corvid_vector --test oct` re-measures every one of those. The
sweep walks the square on a grid four times finer than the encoding's own —
1017 × 1017 points — which puts samples exactly on the `z = 0` seam, exactly on
the outer edges, exactly at the corners and exactly at the centre of every
quantization cell. That last one is where the worst case lives, and it is the
reason random directions are not enough: the seam has measure zero, so a million
uniform directions miss it a million times, and a decoder that clamped instead
of folding would pass a random-only test while being 90° wrong in a corner.

The worst figure is derivable rather than merely observed, which is what says it
is understood. The worst place is the centre of an octahedron face — the
`(±1, ±1, ±1)/√3` directions — because that is where the octahedron's surface
comes nearest the origin, at `1/√3`, so a grid step there subtends the largest
angle. One step of `u` moves the point by `(1, 0, -1)/127` and one of `v` by
`(0, 1, -1)/127`, so a cell centre sits `(0.5, 0.5, -1)/127` from its corner —
a length of `√1.5/127`, all of it perpendicular to the radius. That is
`√4.5/127` radians, or **0.95703°**, against 0.956822° measured — the same to
three digits, and the two thousandths of a degree between them is the
linearisation: the derivation treats a cell as flat and its diagonal as an arc,
and both approximations run slightly high.

The seam and the outer edges get bounds of their own rather than being held to
the number above. They are the places a fold done wrong is worst, and they are
also places where the octahedron is *further* from the origin than a face centre
is, so their true error is a third and a half below the global worst — a bound
borrowed from the face centres would leave enough headroom for a regression
localised to the fold to pass the test written to catch it.

Most of that is the price of sixteen bits rather than a defect in this
implementation, and there is a floor to say how much. Sixteen bits name 65 536
directions, so covering the sphere at all needs each to stand for a patch of
`4π/65536` steradians; a spherical cap of that area has an angular radius of
0.4476°, and no arrangement of 65 536 points can have a smaller covering radius
than a packing of caps. **No 16-bit encoding of a unit vector, however cleverly
laid out, has a worst case below about 0.45°** — this one is 2.14 times that,
which is what the octahedron's distortion between its face centres and its
corners costs. `tests/oct.rs` computes the floor and the ratio.

What that is worth in a frame is a judgement rather than a measurement, and it
depends on the shading. A degree of normal error moves a specular highlight
visibly on a smooth surface; on the faceted, flat-shaded look this workspace is
built for, a face's normal is constant and the error is a uniform shift in one
facet's brightness. Reach for [`Direction`] where it matters.

### It is a wire format

A vertex buffer holds these, so the bytes are frozen in `tests/wire.rs` like
every other encoding here. Two `Signed8` laid out `#[repr(C)]` *is* `wgpu`'s
`Snorm8x2`, byte for byte, which is why the type is a pair of components rather
than one `u16`: a vertex shader reads it as a `vec2<f32>` in `[-1, 1]` with no
shift, mask or bias. The same argument keeps [`Direction`] on `Signed32` rather
than moving it to `I2F30`.

One property a mesh pipeline depends on and a round trip cannot see: decoding a
normal and encoding it again never moves the direction. It does not always
return the same *code* — 507 of the 65 025 canonical codes come back as a
different one, every one of them with a component at `±127`, where the fold
zeroes the other coordinate and the sign it carries is then arbitrary. Two codes,
one direction, and the encoder picks between them consistently. The test walks
all 65 025 to say so.

## Features

Every integration is optional and off by default.

| Feature | Effect |
|---|---|
| `mint` | `From`/`Into` for `mint::Vector3<f32>` and `mint::Vector3<f64>` |
| `nalgebra` | Conversions to and from `nalgebra::Vector3<f64>` |
| `serde` | `Serialize`/`Deserialize`, transparently as a fixed-size array of components |
| `bytemuck` | `Pod` and `Zeroable` |
| `arbitrary` | `Arbitrary`, for fuzzing (links `std`) |
| `std` | Forwards `std` to whichever of the above are enabled |

The crate is `no_std` under every feature except `arbitrary`, whose derive emits
`::std` paths.

`serde` and `bytemuck` cover [`OctDirection`] too — a packed normal is two
bytes under both, which is what makes a vertex buffer and a capture the same
thing.

`Hash` is derived, and each component carries its own encoding — so a
[`Direction`] whose component arrived as `Signed32`'s denormal `-1.0` digests as
the direction it denotes, exactly as it compares.
